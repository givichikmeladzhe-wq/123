Control, Operational State, Memory & Audit Layer

Единая спецификация слоя, который превращает разговоры в управляемую работу, поддерживает текущее состояние проектов в Notion, сохраняет первоисточники и доказательный след в Obsidian, проводит ежедневные briefing и не допускает активацию новых «мозгов» агентов без явного утверждения Андрея.

Документ расширяет существующую архитектуру и не меняет роли Hermes, Codex, RAG и Work молча.

Notion = текущая работа

Проекты, задачи, решения, вопросы, агенты, версии, инструкции и видимый журнал изменений.

Obsidian = источник и аудит

Сырые разговоры, транскрипты, operational packages, briefing и append-only события с hash.

Approval обязателен

Hermes может предложить новую версию мозга, но активировать можно только точный hash, утверждённый Андреем.

Основное решение

Слой строится вокруг одного правила: разговор не меняет систему напрямую. БОТ-расшифровщик создаёт доказательный операционный пакет; Hermes проверяет проект, источники, дубликаты и полномочия; все смысловые изменения проходят через контролируемый State Adapter, фиксируются как ChangeEvent и связываются с сырым источником в Obsidian.

2. Architecture Change Proposals — требуют отдельного утверждения
ACP-001 · Pending

Partitioned State Authority

Изменение: Notion становится authority для mutable Projects/Tasks/Decisions/Open Questions/операционных статусов; control-repo остаётся authority для TaskEnvelope, Run/Result, Agent Manifest, активных prompt-artifacts, кода и evidence.

Причина: оперативная работа должна быть видима и редактируема Андреем без ручного чтения Git-файлов.

Последствия: нужен State Adapter, correlation IDs, сериализованный per-entity single-writer с lease/fencing token, durable transactional store, write policy, reconciliation и миграционная точка cutover.

До approval: Notion — проекция; baseline-authority control-repo не меняется.

ACP-002 · Pending

Obsidian Raw & Audit Authority

Изменение: Obsidian Vault получает формальную роль канонического raw memory и append-only audit trail.

Причина: каждое решение и изменение должно восстанавливаться до первоисточника.

Последствия: Git-backed vault, hashes, retention, backup, запрет update/delete для service accounts.

Ограничение: v1 tamper-evident; настоящий WORM потребует отдельного защищённого storage и нового ACP.

ACP-003 · Pending

Contract Family Extension

Изменение: к существующим TaskEnvelope, ContextManifest, RunEvent и ResultEnvelope добавляются SourceEvent, OperationalPackage, ChangeEvent, ApprovalEvent и BriefingPacket.

Причина: raw source, semantic mutation и approval невозможно надёжно выразить только task/run-контрактами.

Последствия: новые schema versions, validation и adapters; существующие четыре контракта не меняют смысл.

Рекомендуемое решение эксперта: утвердить все три ACP вместе. Они образуют один непротиворечивый слой. Частичное утверждение ACP-001 без ACP-002 оставит оперативное состояние без доказательного следа; ACP-002 без ACP-003 не даст строгой связи события с изменением.

3. Цели, границы и критерии успеха

В scope v1

  • приём raw разговоров, созвонов, голосовых заметок, переписок и транскриптов;
  • формирование структурированного OperationalPackage;
  • Hermes ingest, project resolution, deduplication и создание draft operational entities;
  • 11 связанных Notion data sources;
  • append-only Obsidian Vault с source/audit/snapshots;
  • семантический audit old/new с initiator/reason/source/time;
  • approval и активация версий мозгов/промптов;
  • ежедневный 10–15-минутный briefing по активным проектам;
  • интеграция с Hermes, Codex, Work, RAG, Telegram, n8n и GitHub/control-repo.

Не входит в v1

  • перепроектирование product delivery pipeline и ролей code owner/QA/release;
  • хранение кода, secrets, аудио-байтов или всей RAG-базы внутри Notion;
  • автоматическое утверждение решений, architecture changes или agent brain;
  • индексация сырых транскриптов в RAG без curation;
  • WORM/юридически сертифицированный архив;
  • автоматическая коррекция противоречивого Notion state без review;
  • прямые смысловые writes агентов через Notion MCP в обход State Adapter.

4. Целевая топология слоя
Разговор / созвон / чат→ БОТ-расшифровщик→ Obsidian Raw + OperationalPackage→ Hermes Ingest→ Durable Store + entity lease→ State Adapter / Write Dispatcher→ Notion + Audit Writer
Control plane

Hermes

Планирует briefing, принимает packages/events, разрешает проект, применяет policy, создаёт draft state, запускает исполнителей и approval. Не становится базой данных.

Operational plane

Notion

Текущее человекочитаемое состояние и рабочие очереди. Все agent writes проходят audited State Adapter.

Memory & audit plane

Obsidian + Git

Raw sources, packages, briefing, approvals, audit events и snapshots. Записи не редактируются на месте.

Execution plane

Codex / Antigravity

Получают approved ContextManifest/TaskEnvelope, выполняют работу и возвращают ResultEnvelope. Notion не заменяет repo.

Knowledge plane

RAG

Индексирует только approved/curated knowledge с source_ref и version. Live status и raw conversation не являются knowledge.

Human plane

Андрей / Work / Telegram

Андрей утверждает; Work анализирует и предлагает; Telegram доставляет briefing и single-purpose approval actions.

Coordination plane

SQLite WAL на Hermes Base

Durable commands, outbox, inbox, idempotency, per-entity leases и replay checkpoints. Это системное хранилище восстановления, а не project memory.

Неподвижная граница: Notion сообщает «что сейчас происходит», Obsidian доказывает «откуда это взялось и как менялось», control-repo исполняет «какая точная техническая версия запущена».

Canonical Hash Contract: AIOS-HASH-V1

Каждое поле hash сопровождается hash_profile = AIOS-HASH-V1. Формат digest: sha256:<64 lowercase hex>. Hash без указанного profile не допускается к approval, integrity check или replay.

8. БОТ-расшифровщик: функциональное ТЗ

Назначение

Преобразовать разговор, созвон, голосовую заметку, переписку или готовый transcript в два связанных артефакта: неизменённый первоисточник и структурированный OperationalPackage. Бот не является Hermes, Project Manager или authority.

Pipeline

  1. Intake. Получить файл/текст/ссылку, actor, время и project hint; вычислить idempotency key.
  2. Raw persistence. До анализа записать SourceEvent и raw content в Obsidian; большие audio/video — в File Bridge с checksum manifest.
  3. Transcription. Если вход не текстовый — создать transcript с speaker labels и timestamps; неопознанные участки отметить, не додумывать.
  4. Extraction. Выделить решения, задачи, обязательства, изменения процессов/ответственности, кандидаты инструкций агентам, риски, противоречия, вопросы и следующее действие.
  5. Grounding. Каждый extracted item получает цитируемый anchor: timestamp, message ID или block ID.
  6. Validation. JSON Schema, обязательные поля, отсутствие orphan items, content hash, явное разделение explicit/inferred.
  7. Delivery. Сохранить OperationalPackage в Obsidian и отправить Hermes событие operational_package.ready.

Hermes ingest

  1. проверить signature/hash/schema/idempotency;
  2. сопоставить проект; при confidence ниже порога — создать NEEDS_PROJECT, ничего не применять;
  3. найти дубли и существующие Task/Decision/Question;
  4. создать DRAFT Task/Open Question; explicit Decision — PROPOSED, inferred Decision — NEEDS_REVIEW;
  5. кандидат изменения мозга направить в Brain Version workflow;
  6. применить операции через State Adapter, получить ChangeEvents и audit paths;
  7. пометить package INGESTED и сохранить результат маппинга.

Обязательные негативные правила

  • не объединять два проекта только из-за похожих терминов;
  • не превращать обещание «подумаю» в Task со статусом READY;
  • не считать вопрос решением;
  • не назначать Андрею или агенту обязательство без явного speaker/anchor;
  • не переписывать raw transcript после extraction;
  • не отправлять весь transcript Codex: только ContextManifest и релевантные source excerpts.

Write-once policy

  • каждый raw/audit файл создаётся один раз по стабильному ID;

11. Журналирование смысловых изменений Notion

Контролируемая agent/API mutation

  1. Hermes создаёт StateCommand с entity_key, expected_state_version, reason, source refs, correlation ID и idempotency key.
  2. State Adapter в одной SQLite transaction регистрирует command/inbox, проверяет idempotency и получает lease на entity_key = entity_type:entity_id с новым монотонным fencing_token.
  3. Если lease уже принадлежит другому живому worker, команда остаётся в очереди. Одновременно для одного entity выполняется только один StateCommand; разные entities могут обрабатываться параллельно.
  4. Worker читает текущую entity через notion_state_adapter, нормализует semantic fields по AIOS-HASH-V1, проверяет actor, policy/approval и expected_state_version. Version mismatch прекращает команду без write.
  5. В одной SQLite transaction сохраняются command state PREPARED, before snapshot/hash и outbox intent. Только после durable commit разрешён внешний Notion call.
  6. Непосредственно перед write Adapter повторно проверяет lease/fencing token и актуальную State Version; затем одним request изменяет только перечисленные в patch semantic properties, увеличивает State Version ровно на 1, записывает Last Command ID и временный Audit Status = AUDIT_PENDING.
  7. Adapter повторно читает entity, строит exact old/new diff и after hash. Неожиданное состояние или конкурирующая UI-правка переводят command/entity в UNRECONCILED, а не объявляются успешным exact change.
  8. Audit Writer создаёт immutable CHG-ID в Obsidian и Git commit; outbox сохраняет результат/attempt до подтверждения.
  9. Notion Changes получает searchable projection, target entity — Last Change и Audit Status COMMITTED. Это projection-only metadata update с тем же Last Command ID: он не увеличивает semantic State Version и не создаёт второй ChangeEvent. Command становится COMMITTED, outbox — ACKED.
  10. Lease освобождается только после durable terminal state. При crash он истекает; следующий worker получает больший fencing token, а stale worker больше не может продолжить write.
  11. Только после COMMITTED privileged downstream action может продолжиться.

Per-entity single-writer / lease contract

  • lease_key равен стабильному entity_type:entity_id; одна активная lease на key;
  • acquire/renew/release выполняются транзакционно в SQLite; acquire выдаёт монотонно возрастающий fencing_token;
  • каждая стадия StateCommand проверяет owner, token и expiry; token меньше текущего считается stale и отклоняется;
  • TTL задаётся ENTITY_LEASE_TTL_SECONDS, heartbeat выполняется не реже чем за треть TTL; зависшая команда после expiry может быть продолжена только recovery worker;
  • expected_state_version остаётся обязательным, но является второй защитой после single-writer;
  • в v1 только один Notion Write Dispatcher внутри State Adapter держит notion_state_adapter credential и выполняет remote API calls; Hermes и command workers credential не получают;
  • Dispatcher не отправляет второй write для entity, пока предыдущий имеет состояние WRITE_DISPATCHED/OUTCOME_UNKNOWN. Истечение lease во время network call запускает outcome reconciliation, а не параллельный повтор;
  • ручной Notion UI edit не участвует в lease protocol, поэтому требует pre-write reread, post-write verification и webhook reconciliation.

  • обязательная версия SQLite: 3.51.3+; startup gate проверяет фактически bundled runtime version. Более ранний runtime запрещён из-за исправленного WAL-reset defect;
  • обязательные SQLite settings: journal_mode=WAL, synchronous=FULL, foreign_keys=ON, ограниченный busy_timeout; приложение проверяет возвращённые значения PRAGMA, а не предполагает их применение;
  • command intent и outbox record создаются одной local transaction до external side effect;
  • после restart worker поднимает незавершённые commands/outbox, проверяет фактический внешний state и продолжает state machine идемпотентно;
  • backup выполняется SQLite Online Backup/API в зашифрованное off-host location по расписанию не реже 15 минут и перед deploy/migration; restore тестируется ежемесячно;
  • v1 deployment invariant — один Hermes Base host, использующий этот DB. Переход к нескольким Hermes hosts требует PostgreSQL/эквивалентного transactional store и отдельного Architecture Change Proposal.

Прямая правка Андрея в Notion UI

  1. Notion webhook проходит HMAC-SHA256 signature validation и idempotency по webhook event ID.
  2. Reconciler получает authors, timestamp, updated property IDs и entity ID.
  3. Поскольку webhook не содержит полного old/new, Reconciler получает latest entity через API и сравнивает с последним shadow snapshot.
  4. Фиксируется один semantic diff «последнее подтверждённое состояние → текущий final state».
  5. Если authors несколько, event пришёл не по порядку, snapshot отсутствует или concurrent state ambiguous — Change получает UNRECONCILED; Hermes не действует по нему до review.
  6. Если reason отсутствует, создаётся Open Question NEEDS_REASON; правка видна, но privileged action не запускается.

Гарантия manual UI audit: для State Adapter writes система гарантирует exact old/new. Для прямого UI-edit контракт — best-effort exact reconstruction по последнему trusted shadow snapshot и доступным webhook events. Если точную промежуточную историю, порядок или initiator доказать нельзя, система обязана записать UNRECONCILED; запрещено выдавать восстановленный final diff за доказанную exact sequence.

Notion webhook constraints, учтённые в реализации

  • webhook — сигнал, а не полный diff; latest content нужно получать API-вызовом;
  • частые изменения агрегируются, доставка обычно до минуты, но допускается до 5 минут;
  • события могут приходить не в хронологическом порядке;
  • повторная доставка возможна при неуспешном acknowledge; использовать event ID и attempt number;
  • page.properties_updated содержит authors и IDs изменённых properties, что помогает reconciliation;
  • API rate limit в среднем 3 request/sec; очередь уважает HTTP 429 и Retry-After.

12. Approval workflow и versioning мозгов/промптов
Hermes proposal→ Candidate artifact + diff→ Evaluation→ Approval Андрея→ Hash check + activation→ Health / rollback
  1. Proposal. Hermes создаёт Brain Version DRAFT с причиной, источником, target agent, base version и risk. Он не редактирует ACTIVE version на месте.
  2. Candidate. Назначенный технический владелец создаёт immutable candidate в control-repo, diff и SHA-256; Notion status = PROPOSED/EVALUATING.
  3. Evaluation. Минимальный regression/eval pack проверяет ожидаемое поведение, запреты, tools/permissions и known failure cases.
  4. Request. Hermes формирует краткую approval card: что меняется, зачем, риск, eval, diff, текущая/новая version, rollback target и exact hash.
  5. Decision. Только allowlisted Андрей инициирует APPROVE/REJECT: основной канал — signed Telegram callback; дополнительный — контролируемая action-ссылка/кнопка в карточке Notion, открывающая Hermes Approval UI/endpoint. Оба пути создают ApprovalCommand. Ручное изменение свойства Status и свободное сообщение «ок» не считаются approval.
  6. ApprovalCommand validation. Проверить approval_id, authenticated actor allowlist, decision, channel, issued_at, TTL, single-use token ID, target/version, commit SHA, byte length, AIOS-HASH-V1 и exact artifact hash.
  7. Status mutation. Только State Adapter под entity lease меняет PENDING → APPROVED/REJECTED и создаёт ApprovalEvent + audit. Прямая UI-правка protected field получает UNAUTHORIZED_PROTECTED_EDIT, откатывается к последнему COMMITTED status через Adapter и уведомляет Андрея.
  8. Pre-activation gate. Проверить status APPROVED, actor, expiry, single-use token, exact target/version/commit/length/hash profile/hash, audit COMMITTED и unchanged candidate.
  9. Activation. Контролируемый config release меняет active pointer в Agent Manifest; создаёт commit/activation event. Hermes не переписывает содержимое artifact.
  10. Post-check. Smoke/eval + heartbeat. При failure status ACTIVATION_FAILED и автоматический rollback только на заранее утверждённый known-good hash; событие фиксируется.

13. Ежедневный 10–15-минутный briefing pipeline

Eligibility и подготовка

  1. Hermes scheduler выбирает Projects со Status ACTIVE/OPERATING и Briefing Enabled = true.
  2. Для каждого проекта использует его IANA timezone и Briefing Window; глобальная timezone не предполагается.
  3. Создаёт BRF-ID и фиксирует input state snapshot/hash.
  4. Собирает изменения после предыдущего briefing: completed ResultEnvelope/evidence, status changes, blockers, health, unanswered questions, pending approvals, next 24h.
  5. Проверяет source/audit integrity. Элемент без evidence помечается, а не выдаётся как завершённый факт.
  6. Доставляет в Telegram кнопку «Начать briefing» и компактную повестку.

После briefing

  1. Запись/переписка сохраняется как raw SourceEvent.
  2. БОТ-расшифровщик создаёт OperationalPackage, используя BRF-ID и project_id.
  3. Hermes reconciles package с input snapshot и текущим state; возникшие за время разговора конфликты помечаются.
  4. State Adapter создаёт draft tasks/questions/decisions и ChangeEvents.
  5. Hermes отправляет Андрею close-out: принятые решения, созданные задачи, вопросы, что требует approval, следующий briefing.
  6. Briefing status = CLOSED только после raw source, package, mapping result и audit COMMITTED.

Если briefing пропущен: status = SKIPPED, решений не создаётся, Hermes предлагает новое окно. Молчание или отсутствие Андрея не считается согласием.

Security requirements

  • notion_read и notion_state_adapter используют разные credentials/service principals; read-profile технически не имеет create/update/archive capability;
  • если готовый Notion MCP не умеет гарантированно скрыть write tools/capability, он не подключается к агентам: перед ним ставится custom read-only MCP proxy, регистрирующий только search/fetch;
  • write-profile доступен только State Adapter, ограничен allowlist data sources/properties и не передаётся Hermes, Work, Codex, n8n или prompts;
  • startup/CI negative permission test обязан доказать, что notion_read получает access denied на semantic write; при появлении write tool production gate закрывается;
  • Notion webhook использует отдельный secret и обязательную signature validation;
  • Telegram approval — allowlist exact user ID Андрея, signed single-use callback, expiry;
  • tokens/API keys не хранятся в Notion, Obsidian, transcript или RAG; только secret manager/environment;
  • PII/sensitive sources получают sensitivity + retention class; RAG ingestion отключён по умолчанию;
  • Audit Writer и Transcriber не имеют production credentials;
  • Hermes не получает право hard delete; operational deletion заменяется archive + audit;
  • SQLite online backup не реже 15 минут и перед deploy; ежедневный backup Notion export/snapshots и Git push Vault; ежемесячный end-to-end restore test;
  • schema changes Notion разрешены только через отдельную migration Task и ACP/Decision при изменении semantics.

Deterministic Recovery / Replay Contract

Replay восстанавливает semantic operational state и его Notion projection; он не пытается восстановить рассуждения или историю чата Hermes.

Approved schema snapshot→ Latest trusted checkpoint→ Ordered ChangeEvents→ Hash/version integrity→ control-repo reconcile→ Rebuild Notion projections
  1. Freeze scope. Перевести восстанавливаемый project/entity set в maintenance mode и получить replay/entity leases; новые semantic writes для scope ставятся в очередь.
  2. Load schema. Загрузить approved schema/contract version из control-repo и проверить immutable schema snapshot/hash в Obsidian.
  3. Select checkpoint. Для каждой entity взять последний trusted checkpoint: entity_key, schema_version, state_version, state_hash, last_change_id. Trusted означает valid AIOS-HASH-V1, COMMITTED audit и непротиворечивую Git history.
  4. Build event chain. Выбрать последующие COMMITTED ChangeEvents. Канонический порядок внутри entity задаётся парой state_version_before → state_version_after, а change_id служит tie-breaker только после доказанной непрерывности. occurred_at используется для отображения и диагностики, но не определяет replay order.
  5. Continuity gate. Первый event обязан начинаться с checkpoint version/hash; каждый следующий — с version/hash предыдущего; нормальный переход увеличивает version ровно на 1. Gap, duplicate branch, два разных events с одним state_version_before или before-hash mismatch останавливают replay и создают integrity incident.
  6. Apply. Проверить schema, source refs и hashes; применить normalized old→new patch; пересчитать after hash по AIOS-HASH-V1 и сравнить с event.
  7. Reconcile executable state. Для TaskEnvelope, Agent Manifest, brain/config/code сверить control-repo commit SHA и exact artifact hash. Несовпадение блокирует ACTIVE/DONE projection.
  8. Rebuild projection. State Adapter в REPLAY_PROJECTION mode под entity lease создаёт/обновляет Notion до reconstructed state. Idempotency key = replay_id:entity_key:state_version. Projection write не создаёт новый semantic ChangeEvent; создаётся отдельный system replay event.
  9. Verify and unfreeze. Сравнить reconstructed hash/state_version с Notion, control-repo и latest audit; сохранить integrity report/checkpoint; только затем снять maintenance mode.

Recovery after SQLite loss: сначала восстановить последний валидный SQLite backup. Затем recovery worker сверяет незавершённые commands/outbox с Notion state, Obsidian ChangeEvents и idempotency keys. Изменение Notion без доказанного audit становится UNRECONCILED; replay не придумывает недостающий event.

18. Основания и технические источники

Архитектурный baseline: AI_OS_Interaction_Architecture_v1.html, SHA-256 указан в разделе 1. Новое ТЗ не перезаписывает baseline.

  • Notion Data source — data sources и properties; разделение database/data source введено API version 2025-09-03.
  • Notion Update page — обновление properties, capabilities и актуальный Notion-Version: 2026-03-11.
  • Notion Webhooks — HTTPS endpoint, verification и HMAC-SHA256 signature.
  • Notion Event types & delivery — aggregation, ordering, retries, authors и отсутствие полного changed content в webhook.
  • Notion page.properties_updated — entity, authors и updated_properties.
  • Notion Request limits — средний лимит 3 request/sec, 429 и Retry-After, size constraints.
  • Obsidian URI — ссылки на vault/file/heading/block.
  • Obsidian Sync Version history — дополнительная version history с ограниченным retention; поэтому audit опирается на Git/hash.
  • RFC 8785: JSON Canonicalization Scheme — нормативная canonical JSON serialization для AIOS-HASH-V1.
  • SQLite Write-Ahead Logging — WAL, same-host constraint, single DB writer, checkpointing, FULL sync и требование patched SQLite 3.51.3+.
  • SQLite Online Backup API — согласованный snapshot работающей database без простого копирования live DB-файла.
  • SQLite PRAGMA synchronous — durability settings, проверяемые при startup.
